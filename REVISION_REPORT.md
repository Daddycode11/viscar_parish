## Changes and setup

Shared guards enforce authenticated roles, parish/owner scope and CSRF before existing handlers. Transactional booking/payment/request helpers validate state and persist synchronized changes. Local QR verification and event check-in reuse booking tokens; certificate issuance preserves existing numbers. Additional-document requests now persist and have an owner upload/review path. Reports use database aggregates, including zero-revenue handling. FAQ automation reuses approved parish FAQs and existing messages with staff handoff. Login security adds optional email OTP.

The local schema received additive migrations; existing records were preserved. Local configuration values were retained separately from shared configuration helpers. [Local setup and reminder instructions](LOCAL_SETUP.md) describe the existing Apache port, migration command and local-only transport logs. Shared implementation files are listed per requirement below.

## Acceptance limits

Live payment transfer, actual SMS/email delivery, scheduled deployment execution, physical scanners/printers and production infrastructure encryption were not exercised. Browser checks used Chrome with external network resources blocked. Concurrency rules use database transactions and row locks; simultaneous multi-worker load was not stress-tested. Two-factor throttling is session-based and needs deployment-level rate limiting. PDF output uses existing print/save-to-PDF templates. These limits are not reported as missing implementations.

The optional assistant uses conservative token matching against stored FAQ answers; it does not generate new parish policies or fees. Literal JWT and infrastructure encryption remain open items rather than false completion marks.
